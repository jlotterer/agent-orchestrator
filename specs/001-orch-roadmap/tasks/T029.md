# T029: Settings forms in the dashboard, driven by one settings schema

## Goal
Server settings live in `$ORCH_HOME/server.json` and project settings in `<repo>/orch.config.json` (decision 0013); both are edited by hand today and documented by hand in architecture §19 and two user-guide reference pages, which drift. When this task is done, `src/settings-schema.ts` describes every setting once (path, scope `server`|`project`, type, default, enum values, description, group, `secret`, `restart`), the loaders take their defaults from it, a unit test proves the §19 table and the schema name the same keys, and the dashboard has a **Settings** tab with a Server form and a Project form generated from the schema. Saving validates with the same loaders as startup, writes the same two files, hot-reloads the server config where no restart is needed, and commits a project's file to its base branch. Secrets are write-only. Decision record 0026 records that settings stay in the two files, never in SQLite, and that the schema is their single description.

## Acceptance criteria
- Given `settingsSchema` exported from `src/settings-schema.ts`, When `test/unit/settings.test.mjs` builds the defaults from it, Then they deep-equal `DEFAULT_SERVER_CONFIG` and `DEFAULT_PROJECT_CONFIG`, and the set of dotted keys in the architecture §19 table (parsed from `docs/architecture.md`) equals the schema's keys, both ways, excluding the env-var rows.
- Given `GET /api/settings/schema`, Then it returns the schema entries; given `GET /api/settings/server`, Then every `secret` entry (`auth.token`, `notify.ntfyToken`, each `agents.adapters.*.env` value) is returned as `{set: true|false}` and never its value.
- Given `PUT /api/settings/server` with a body that keeps a secret masked or omits it, Then the stored value is kept; with a body that fails `loadServerConfig`'s rules or names a key outside the schema, Then 400 with that message and `server.json` unchanged; with a valid body, Then `server.json` is rewritten (2-space JSON, atomic rename) and the response is `{ok, restartRequired: [<keys with restart: true that changed>]}`.
- Given a valid PUT that changes `agents.roles.validator`, When the next agent launch happens, Then it uses the new role without a restart (`orch.reloadServer()` swaps the config and rebuilds project contexts), while a change to `host`, `port`, `publicUrl`, `auth.*` or `retention.*` is written and reported as restart-required.
- Given `PUT /api/projects/:id/settings`, Then forbidden keys answer 400 with the existing message (§5.2) and nothing is written; a valid body writes `<repo>/orch.config.json`, commits it on the base branch as `chore(orch): update project settings` when the base checkout has no other staged or unstaged change, else writes it and returns `committed: false` with the reason; `refreshContext` runs so the next tick uses it; the response includes the loader's `warnings`.
- Given `POST /api/settings/notify-test`, Then one ntfy message `orch: test notification` is sent with the configured URL and token and the response is `{ok}` or `{ok: false, error}`; the token is not in the response or the event log.
- Given the Settings tab, Then the Server form has groups Agents (adapters with command, extra args and env keys, env values write-only; the role table with the server default and the selected project's override side by side), Notifications (with Send test) and Server (host, port, public URL, token, retention shown read-only with "edit server.json and restart"); the Project form has validation, scheduler, git and roles groups, an Advanced toggle for `handoff.*` and `git.feedback.*`, and a raw JSON editor validated by the same PUT; saving a restart-required key shows a badge until the daemon restarts; `test/unit/dashboard.test.mjs` still parses every script.
- Given `npm run check`, Then it passes: the schema's default adapters are the only vendor names outside `src/adapters/`, allowlisted as `src/config.ts` is today.
