# T028: Agent accounts: sign in to every CLI from the dashboard

## Goal
Today signing an agent CLI into the orch server means `docker compose run`, a browser on another machine and knowing which volume holds what; a login that fails silently (the Gemini case) shows up only as failed tasks. When this task is done, the dashboard has an **Agents** tab listing every adapter in `agents.adapters` plus the GitHub CLI, each with its installed version and signed-in state, and a **Sign in** button that runs that CLI's own login flow headlessly on the server: the URL and code the CLI prints appear in the page, anything the flow asks the owner to type is sent back to it, and when it ends the card shows the new state. Credentials stay in each CLI's own store (the existing volumes); orch stores nothing about a flow. `src/accounts.ts` is the vendor-free engine; each adapter contributes only its status and login commands through a new optional `account` member of `AgentAdapter`. Decision record 0025 explains why orch drives the CLIs' flows instead of holding tokens.

## Acceptance criteria
- Given adapters `claude`, `codex`, `antigravity` in `server.json`, When `GET /api/accounts` runs, Then it returns one row per adapter plus one `gh` row: `{id, kind: "adapter"|"tool", type, command, version, status: "signed_in"|"signed_out"|"unknown", detail, loginActive}`; a command that cannot be spawned gives `version: null`, `status: "unknown"` and `detail` starting with `not installed`; probes run in parallel with a 15 s timeout each.
- Given a fake CLI `scripts/fake-login.mjs` that prints `Open https://example.test/device and enter code ABCD-EFGH`, waits for a line on stdin, then exits 0 and writes a marker file, When `POST /api/accounts/<id>/login` then `POST /api/accounts/<id>/login/input` with `{text: "ok"}` run, Then SSE `account` events carry the URL line and `{id, done: true, exitCode: 0}`, the marker file exists, no event with the URL, the code or `ok` is in the `events` table, and a second `POST …/login` while the first runs returns 409.
- Given a flow that prints ANSI colour codes and echoes its input, When its lines reach the dashboard, Then they are stripped of escape sequences and the echoed input line is not sent.
- Given a running flow, When `POST /api/accounts/<id>/login/cancel` runs or 10 minutes pass, Then the child is killed, a `done` event with the exit code follows, and the status probe runs again.
- Given `platform() !== "linux" && !== "darwin"`, When a login is started, Then the API answers 501 with the exact CLI command the owner can run by hand, and the dashboard shows it.
- Given the Agents tab, When a card's Sign in is clicked, Then a panel shows the streamed lines with `https://` tokens as links and codes with a copy button, a text field plus Send (empty text sends Enter), Cancel, and the card's status refreshes when the flow ends; `test/unit/dashboard.test.mjs` still parses every script.
- Given `AgentAdapter.account` is implemented by `claude` (`claude auth status --json`, `claude auth login`), `codex` (`codex login status`, `codex login --device-auth -c cli_auth_credentials_store=file`) and `antigravity` (probe and login per the contract), Then unit tests check each `parseStatus` against recorded outputs, and `npm run check` passes with vendor names still confined to `src/adapters/` (the `gh` commands live in `src/accounts.ts`, which the invariant allows because GitHub is not an agent vendor).
- Manual: in the Docker image on the home server, Claude Code, Codex and gh are each signed in through the panel with the owner's subscription accounts, and a run then completes a task with no `docker compose run` step; the PR records each flow's screens, the exact prompt texts observed, and anything the contract marked **verify**. Antigravity follows T027's finding: a Sign in button when the keyring works, API-key instructions otherwise.

## Out of scope
- Editing settings (adapters, roles, models) from the dashboard: T029.
- Storing or proxying any vendor token in orch, or a login UI of orch's own: rejected, the CLIs own their credentials (REQ-OPS-07, decision 0025).
- Windows hosts: the API answers 501 with the manual command; no pty emulation.
- Changing how agents are launched or how `runner.ts` spawns them.

## Notes for the worker
Build `accounts.ts` first as an `EventEmitter` with `list()`, `startLogin(id)`, `sendInput(id, text)`, `cancel(id)`; `server.ts` registers the routes and forwards its `account` events to the SSE `send`, next to the existing `event` and `change` types. Spawn flows through `script` as the contract says, with `env` from the adapter config merged like `runner.ts` does, `cwd` = ORCH_HOME. Keep every vendor command in the adapter's `account` member; `accounts.ts` knows only `LaunchSpec`s and the `gh` pair, and reads `git.ghCommand` from the server config. Never call `decide()` or `store` from this module: a sign-in is not an orchestration event (REQ-OPS-08). In the dashboard, add the tab beside Activity, reuse the drawer styles, and render from the `/api/accounts` rows so a new adapter needs no UI change. Add the routes to architecture §15.1 and the panel to §15.3, the `account` member to §13, and `0025` to the decisions index; in docs/docker.md and the user guide make the panel the primary sign-in path and keep the CLI commands as the fallback. Requirements: set REQ-UI-09 and REQ-OPS-08 to built. Tick T028 in `specs/001-orch-roadmap/tasks.md` and the index row in `docs/tasks/README.md`.
